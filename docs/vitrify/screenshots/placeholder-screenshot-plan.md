# vitrify app screenshot plan

The vitrify promotional website will use real screenshots from the current functioning Flutter app.

The app is not concept-only. It already works.

The current UI is functional but visually unfinished. The screenshots should therefore be treated as:

1. proof that the product exists
2. evidence of current functionality
3. material for UI critique
4. a bridge toward the future design system

They are not fake placeholder screenshots.

---

## Purpose

The screenshots should help show what vitrify already does while also guiding what the app UI needs to become.

They should document:

- working piece records
- working production states
- working firing flows
- working failure recording
- working stock logic
- working student/class/client/order contexts where available
- existing app structure
- current UI weaknesses
- future design-system targets

---

## Important positioning

The promo site should not pretend that the current raw UI is the final design.

Instead, the private promo/design site can use current screenshots in one of three ways:

1. as product proof
2. as annotated current-state screenshots
3. as before/after material once redesign mockups exist

The site may say internally:

Current app function exists.  
Final visual system is being defined.

Do not publish public-facing copy that makes the unfinished UI look like the final brand.

---

## Screenshot types

### 1. Current-state screenshots

These are direct screenshots from the Flutter app.

Use them to show:

- the product works
- the logic exists
- the workflows are real
- the app is not a fantasy landing page

Label internally as:

current app UI

---

### 2. Annotated screenshots

These are current screenshots with notes.

Use annotations to identify:

- what the screen does well
- what is visually weak
- what needs redesign
- what component should replace the current UI
- what belongs to the future design system

Annotations should be precise and useful, not insulting.

---

### 3. Future redesign targets

These are later mockups or redesigned app screens based on the design foundation.

Use them to show:

- target component language
- improved visual hierarchy
- better mobile layout
- off-tone pastel labels
- ledger structure
- cleaner rows
- better chips
- better forms

These should eventually replace raw screenshots on the public promo site.

## Required real screenshots

### 1. Today / queues

Purpose:

Show what needs attention now.

Capture:

- pieces waiting for firing
- pieces waiting for glazing
- ready pieces
- failed pieces needing action
- grouped pieces if available
- current operational queue logic

Product question:

What needs attention now?

---

### 2. Pieces list

Purpose:

Show physical pieces as the central product object.

Capture:

- piece list
- grouped pieces if available
- production state labels
- context labels
- search/filter if available
- current row/card structure

Product question:

What exists?

---

### 3. Piece detail

Purpose:

Show the individual physical-object record.

Capture:

- piece name
- state
- context
- notes
- firing history
- failure history if available
- stock/commercial status if available
- correction/edit actions

Product question:

What do we know about this piece?

---

### 4. New piece flow

Purpose:

Show how records enter the system.

Capture:

- piece type selection
- context/purpose selection
- quantity
- color/attribute selection if available
- linked student/class/client/order if available
- create action

Product question:

How does the atelier record new physical work?

---

### 5. Firing batch / firing flow

Purpose:

Show that firings are real batch events.

Capture:

- choose kiln
- choose firing type
- loaded pieces
- batch review
- completion flow
- outcomes
- failed pieces if available

Product question:

What entered the kiln, and what happened after?

---

### 6. Failure recording

Purpose:

Show that failure is recorded as an outcome.

Capture:

- mark failed flow
- failure details
- category/reason
- notes
- loss/remake fields if available
- resulting history

Product question:

What failed, where, and what should happen next?

---

### 7. Stock

Purpose:

Show that stock is derived from real pieces.

Capture:

- ready stock
- reserved pieces
- sold/delivered/missing/failed if available
- stock grouping
- available count logic

Product question:

What is actually available?

---

### 8. Statistics / history

Purpose:

Show the long-term value of recording.

Capture:

- production counts
- failure/loss reports
- firing outcomes
- stock movement
- glaze/form performance if available
- operational summaries

Product question:

What has the atelier learned over time?

---

## Screenshot use on the private promo site

Because the site is private, current screenshots can be used more openly.

Use them to:

- test page rhythm
- test image placement
- identify app UI redesign priorities
- document what exists now
- create before/after comparisons later

For the public version, review every screenshot before launch.

---

## Visual treatment

Current raw screenshots should not be over-decorated.

Use:

- simple frames
- thin borders
- captions
- sparse annotations
- current-state labels
- design-target labels when relevant

Avoid:

- pretending raw UI is final
- hiding key functionality under decorative mockups
- 3D phone renders
- heavy shadows
- ceramic-themed presentation
- fake polish

---

## Data safety

Even if screenshots are real, they must not expose private data.

Before using screenshots, check for:

- real student names
- real client names
- real order details
- real private notes
- real email addresses
- phone numbers
- private atelier data
- sensitive business numbers

If needed, use demo data or blur/crop sensitive fields.

---

## App redesign use

Each screenshot should produce design questions:

- Is the hierarchy clear?
- Are the actions obvious?
- Are states readable?
- Are labels too large?
- Are buttons too big?
- Is the page too card-heavy?
- Does it feel like a real production ledger?
- Where should off-tone pastel labels appear?
- What should become a reusable Flutter component?

The screenshots should become the raw material for the Flutter UI redesign.

---

## Final rule

The screenshots are real product evidence.

They are allowed to look unfinished during private design work.

The goal is not to hide the current app.

The goal is to use the current app as the foundation for a better visual and interaction system.
